Part A – Resource group and NSG (≈ 20 min, FREE)

Step 0: Sign in and check capacity

  1. Go to portal.azure.com, sign in, and check the directory under your name is Default Directory.

  2. Check the VM size is still available in zones 1 and 3 (2 minutes – avoids building everything and then failing at the VMs). In your terminal:

    az vm list-skus --location eastus2 --size Standard_D2als_v6 \
  --query "[0].{Zones:locationInfo[0].zones, Restricted:restrictions[].restrictionInfo.zones}" -o json

    Use two zones that appear under Zones but not under Restricted. The walkthrough uses 1 and 3; swap in others if needed.

    Why D2als_v6 and zones 1 and 3? The original plan used Standard_D2s_v3 in zones 1 and 2, but a zone check showed D2s_v3 – and most other small sizes – restricted in every zone for this subscription in East US 2. Of the sizes checked, only Standard_D2als_v6 (2 vCPU, 4 GB, AMD) was allowed in zones, and only in 1 and 3.

  3. Check your quota: az vm list-usage --location eastus2 -o table | grep -iE "Dalv6|Dalsv6|Total Regional". Two D2als_v6 need 4 free vCPUs in that family (the limit was 10, with none used).

Step 2: NSG – deliberately WITHOUT a web rule (yet)

  1. Search Network security groups → + Create → RG rg-az104-project06, Name nsg-web, Region East US 2, tags → Create.
  2. Open nsg-web → Settings → Inbound security rules → + Add. Add only these two (Source port ranges always *):
Priority Name Source Source value Destination Dest. value Service / port Protocol Action
110 Allow-Mgmt-Bastion IP Addresses 10.10.254.0/26 IP Addresses 10.10.1.0/24 Custom, 22,3389 TCP Allow
4000 Deny-VNet-Inbound Service Tag VirtualNetwork Any – Custom, * Any Deny

Why no port 80 rule? Test 1 proves that a Standard Load Balancer is secure by default: the website won’t load until you add the HTTP rule in Part E.

Health probes are already allowed: the default rule AllowAzureLoadBalancerInBound (65001) lets probes from 168.63.129.16 through. Our Deny-VNet-Inbound rule doesn’t block them, because the AzureLoadBalancer tag is separate from VirtualNetwork.

Step 8: Check the VMs and the pool

  1. Load balancers → lb-az104-project06 → Settings → Backend pools → bepool-web shows vm-lb1 and vm-lb2.

  2. Open each VM’s Overview: note the private IP (likely 10.10.1.4 and 10.10.1.5) and Availability zone (1 and 3).

  3. Wait 3–5 minutes for cloud-init, then check Nginx on each VM: VM → Operations → Run command → RunShellScript:

    cloud-init status; systemctl is-active nginx; curl -s http://localhost | grep "Served by"

    Expected: status: done, active, and Served by: vm-lb1 (or vm-lb2).

    If Nginx isn’t installed, run this to install it (uses the outbound rule):

    apt-get update -q && apt-get install -y -q nginx && echo "<h1>Served by: $(hostname)</h1>" > /var/www/html/index.html && systemctl enable --now nginx && echo OK

Part E – Core tests (≈ 30 min) 💰

Use <LB-IP> = the public IP of pip-lb-az104-project06.

Test 1: Secure by default (website BLOCKED)

  1. In your browser, open http://<LB-IP> (http, not https).
  2. Expected: the page doesn’t load (spins, then times out).

Why: the Standard Load Balancer forwards the traffic, but nsg-web has no rule allowing port 80 from the Internet, so the default DenyAllInBound drops it.

📸 Screenshot the browser timing out, with the address bar visible.

Test 2: Allow HTTP – website WORKS

  1. nsg-web → Inbound security rules → + Add:
Priority Name Source Source value Destination Dest. value Port Protocol Action
100 Allow-HTTP-Internet Service Tag Internet IP Addresses 10.10.1.0/24 80 TCP Allow
  1. Wait 30 seconds and refresh http://<LB-IP>.
  2. Expected: the page shows “Served by: vm-lb1” (or vm-lb2) and its availability zone.

📸 Screenshot the page.

The NSG rule’s destination is the VM subnet, not the load balancer’s IP – the load balancer passes traffic through to the VMs, and the NSG on the VMs’ subnet makes the decision. The source stays the visitor’s real IP, which is why Internet matches.

Test 3: Distribution across both servers

Browsers reuse connections, so use your Ubuntu terminal (replace <LB-IP>):

for i in $(seq 1 10); do curl -s http://<LB-IP> | grep -o "vm-lb[12]"; done

for i in $(seq 1 10) repeats 10 times; curl -s fetches the page; grep -o "vm-lb[12]" shows only the server name.

Expected: a mix of vm-lb1 and vm-lb2. Each curl is a new connection with a new source port, so the 5-tuple hash spreads them.

📸 Screenshot the terminal output.

Test 4: Health check and failover

  1. Open vm-lb1 → Run command → RunShellScript:

    systemctl stop nginx && echo "nginx stopped on $(hostname)"

  2. Wait about 30 seconds (the probe checks every 5 seconds).

  3. Run the curl loop again from Test 3.

  4. Expected: only vm-lb2 answers. The website stayed up even though a server failed.

  5. See the probe’s view: lb-az104-project06 → Monitoring → Metrics → Metric Health Probe Status → Apply splitting by Backend IP Address. vm-lb1’s line drops to 0 (unhealthy); vm-lb2 stays at 100.

📸 Screenshot the curl output (only vm-lb2) and the Health Probe Status chart.

Test 5: Recovery

  1. On vm-lb1 → Run command:

    systemctl start nginx && echo "nginx started on $(hostname)"

  2. Wait 30 seconds, run the curl loop again.

  3. Expected: both servers answer again – vm-lb1 rejoined automatically.

Step 10: Allow SSH from YOUR IP only

nsg-web → Inbound security rules → + Add:

Priority Name Source Destination Port Protocol Action
120 Allow-SSH-MyIP-TEMP My IP address IP Addresses → 10.10.1.0/24 22 TCP Allow

The NSG checks the backend port (22), not the frontend port (50001) – the load balancer translates the port before the traffic reaches the subnet.

Step 11: Connect

In your Ubuntu terminal:

chmod 400 ~/Downloads/az104-p06-key.pem
ssh -i ~/Downloads/az104-p06-key.pem -p 50001 azureuser@<LB-IP>
  • chmod 400 makes the key readable only by you (SSH refuses keys that others can read).
  • -p 50001 connects to the load balancer’s port 50001, which forwards to vm-lb1:22.

Type yes to the fingerprint question. You’re now on vm-lb1. Run hostname (shows vm-lb1), then exit.

📸 Screenshot the SSH session showing hostname.

Step 12: Remove it straight away

  1. lb-az104-project06 → Inbound NAT rules → delete nat-ssh-vm-lb1.
  2. nsg-web → Inbound security rules → delete Allow-SSH-MyIP-TEMP.

Security+ point: least privilege (one VM, one port, one source IP), minimal exposure time, and removal afterwards. In production, Azure Bastion (Project 07) avoids opening management ports at all.

What the portal taught you

  • A Standard load balancer is closed until an NSG allows the traffic.
  • The load balancer is Layer 4: it sees IPs and ports, not URLs.
  • Health probes decide which backends get traffic – and come from AzureLoadBalancer (168.63.129.16).
  • VMs join a backend pool through their NIC.
  • Outbound rules give pool members explicit internet access without public IPs.
  • Inbound NAT rules map one frontend port to one VM’s port – useful, but risky if not restricted.
  • Zones spread the VMs across datacenters; a zone-redundant frontend survives a zone failure.
